# Steno v1 program: workstreams, boundaries, verification

Status: orchestration document, written 2026-09-25 by the orchestrating agent.
Scope authority remains [`2026-09-24-initial-scope.md`](2026-09-24-initial-scope.md).
This file fixes the module boundaries and interfaces that the per-workstream
plans build on, so that plans written in parallel fit together. Where a
workstream plan needs to change something here, it says so explicitly at the
top and the change is reconciled before implementation starts.

## Repository layout for v1

```
Package.swift                      one SwiftPM package, Swift 6, macOS 15+
Sources/
  StenoCore/                       canonical model, protocols, GRDB store, pipeline, templates, settings
  StenoAudio/                      capture (tap + mic lanes), echo cancellation, meeting detection, file writers
  StenoSpeech/                     FluidAudio + WhisperKit engines, FluidAudio diarizer, speaker matching
  StenoLLM/                        OpenAI-compatible client, prompt assembly, structured outputs
  StenoAdapters/                   Destination implementations and renderers (Obsidian folder, VTT, JSON, Markdown)
  StenoHandover/                   Mac side of the phone handover: Bonjour advertise, pairing, HTTPS upload receiver
  steno/                           CLI executable: headless pipeline runs, bake-offs, fixture generation
Tests/
  <Target>Tests/                   one test target per module
  Fixtures/                        short synthetic audio, transcripts, template snapshots
apps/macos/                        SwiftUI app, xcodegen project.yml, Sparkle, signing config
mobile/                            Expo iOS recorder (exists; scaffold only)
```

Module dependency direction, strictly one way:

```
StenoCore  <-  StenoAudio, StenoSpeech, StenoLLM, StenoAdapters, StenoHandover  <-  steno (CLI), apps/macos
```

`StenoCore` depends on nothing but GRDB and Foundation. Every other module
depends on `StenoCore` and on its own third-party packages only. The app and
the CLI are the only places that wire concrete implementations together.

Third-party packages: GRDB.swift (storage), FluidAudio (Parakeet, diarization,
embeddings, VAD), WhisperKit (Whisper), Sparkle (app updates, app target only).
Anything else needs a sentence in the plan saying why.

## Canonical model (owned by StenoCore)

Value types, `Codable`, `Sendable`, `Equatable`. Identifiers are `UUID`.
Timestamps are `Date`; in-recording offsets are `TimeInterval` seconds.

- `Meeting`: id, title, startedAt, duration, language (`Locale.Language`), source (`.macCall`, `.macInPerson`, `.phone`), calendarEventID, tags, state (`.recording`, `.queued`, `.processing`, `.ready`, `.failed(reason)`), templateID, summary (markdown), scratchpad, createdAt, updatedAt
- `Participant`: id, meetingID, personID?, displayName, role (`.me`, `.them`), email?
- `Person`: id, displayName, email?, embedding (`[Float]`, 256, L2-normalised), sampleCount, createdAt
- `Speaker`: id, meetingID, clusterLabel, personID?, embedding, sampleClipRange (start, end), confidence
- `TranscriptSegment`: id, meetingID, start, end, speakerID, lane (`.mic`, `.system`, `.mixed`), text, rawText
- `MeetingTask`: id, meetingID, text, assigneePersonID?, assigneeName?, priority (`.low`, `.normal`, `.high`), dueDate?, done
- `Decision`: id, meetingID, text
- `AudioAsset`: id, meetingID, url, format, lanes, durationSeconds, retention (`.deleteAfterProcessing`, `.keepDays(Int)`, `.keepForever`), expiresAt?
- `Delivery`: id, meetingID, destinationID, status (`.pending`, `.delivered(Date)`, `.failed(String, Date)`), lastAttemptAt

GRDB schema mirrors these one table per type, migrations append-only in
`Sources/StenoCore/Storage/Migrations.swift`. Full-text search over segments
and summaries via FTS5 from the first migration.

## Protocols (owned by StenoCore, implemented elsewhere)

Signatures are the contract; plans may add members but must not remove or
rename these without a note at the top of the plan.

```swift
public protocol SpeechEngine: Sendable {
    var id: String { get }                       // "parakeet-v3", "whisperkit-large-v3-turbo"
    var supportedLanguages: Set<Locale.Language> { get }
    func prepare() async throws                  // download / load models
    func transcribe(_ audio: AudioBuffer16k, hint: Locale.Language?) async throws -> [RawSegment]
}

public protocol Diarizer: Sendable {
    func prepare() async throws
    func diarize(_ audio: AudioBuffer16k) async throws -> DiarizationResult   // clusters with time ranges and embeddings
}

public protocol EchoCanceller: Sendable {
    init(sampleRate: Double, frameSize: Int) throws
    func process(nearEnd: UnsafeBufferPointer<Float>, farEnd: UnsafeBufferPointer<Float>, out: UnsafeMutableBufferPointer<Float>)  // real-time safe: no allocation, no locks
}

public protocol LanguageModel: Sendable {
    func complete(_ request: LLMRequest) async throws -> LLMResponse          // request carries messages, optional JSON schema, temperature
}

public protocol Destination: Sendable {
    var id: String { get }
    var displayName: String { get }
    func validate(settings: DestinationSettings) async throws
    func deliver(_ export: MeetingExport, settings: DestinationSettings, mode: DeliveryMode) async throws   // mode: .initial or .reexport
}

public protocol SpeakerMemory: Sendable {
    func match(_ embedding: [Float]) async throws -> (Person, Float)?         // best cosine match above threshold
    func enroll(_ embedding: [Float], as person: Person) async throws
}
```

Supporting types in StenoCore: `AudioBuffer16k` (mono Float32 at 16 kHz plus
sample count), `RawSegment` (start, end, text, language?, wordTimings?),
`DiarizationResult`, `LLMRequest`/`LLMResponse`, `MeetingExport` (the full
meeting plus rendered artefacts), `DestinationSettings` (typed dictionary),
`DeliveryMode`.

## Pipeline (owned by StenoCore, `ProcessingPipeline`)

Input: a finished `AudioAsset` with one or two lanes. Steps, each a separate
type with its own tests:

1. Decode and resample to 16 kHz mono per lane.
2. Transcribe each lane with the configured `SpeechEngine`.
3. Diarize the system lane (or the single lane for in-person and phone).
4. Match clusters against `SpeakerMemory`; unmatched clusters become
   `Speaker` rows with a sample clip range and `personID == nil`.
5. Merge lanes into one ordered transcript. Mic lane segments get the "me"
   participant.
6. LLM pass 1: cleanup (Denglish, casing, product names) on the merged
   transcript, chunked, preserving segment boundaries.
7. LLM pass 2: title, summary from the selected template, decisions, tasks
   with assignee, priority, due date, and speaker name inference from context
   plus calendar attendees. Structured JSON output.
8. Persist. Mark `.ready`. Emit `MeetingReady` event.
9. Deliver to every enabled `Destination` with `.initial`.

Failures in 6 to 7 keep the transcript and mark the meeting `.failed` with a
reason; the user can re-run. Re-running the summary with another template
executes only 7 to 9 with `.reexport`.

## Verification standard for every implementation agent

- Code compiles and tests pass on macOS. Until the Forge runner is registered
  for this repository, the source of truth is the GitHub-hosted `macos-15` job
  in `.github/workflows/swift-ci.yml` (free on this public repository). An
  agent that cannot run Swift locally pushes its branch and reads the run.
- Each PR reports: the CI run URL, the test count, and any test it skipped or
  marked expected-failure and why.
- No real meeting audio in the repository. Fixtures are generated (sine
  sweeps, TTS, or `say` output on macOS) and under ten seconds.
- No network in unit tests. The LLM client is tested against a local stub
  server; engines are tested through a fake conforming to the protocol, with
  one opt-in integration test that downloads models when `STENO_MODEL_TESTS=1`.

## Rules for every plan

- Start with a one-paragraph goal and an explicit non-goals list.
- List the public API the workstream exposes, as Swift signatures.
- List every file to create with one line each.
- Break work into steps of at most a day each, with an acceptance check per
  step that a reviewer can run.
- Name the tests: unit, integration, and the one manual check that only a
  human on a Mac can do.
- Name the spikes that must succeed before the step that depends on them.
- Say what the workstream needs from other workstreams, by protocol name.
- Keep it under 400 lines. Decisions, not prose.
