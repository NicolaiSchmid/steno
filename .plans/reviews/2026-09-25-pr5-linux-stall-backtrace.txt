PR #5 (StenoLLM), correctness review finding 12: the Linux-only stall of
`swift test --parallel --filter StenoLLMTests` on the `steno-swift:6.1`
container (swift-corelibs-foundation / FoundationNetworking). Excerpt of the
lldb `thread backtrace all` taken while attached to the stalled test process;
the two threads below hold each other's lock. Every other thread was parked
behind them. The full dump was 38 threads; only what shows the cycle is kept.

Not a product defect: the shipped macOS build runs on CFNetwork's URLSession,
whose `cancel()` is asynchronous, and the same run completed 14 of 14 times on
a Mac. The Linux loop runs one suite per `--filter` instead.

Thread A: the test task leaving `mapBounded`'s task group after the first
failed map call. `_swift_taskGroup_cancelAllChildren` holds the child's task
status-record lock and, inside it, runs the child's cancellation handler,
which is `URLSession.CancelState.cancel()` -> `URLSessionTask.cancel()` ->
`DispatchQueue.sync` onto the session's work queue. That queue is busy on
thread B, so A blocks while holding the status lock.
